# Product requirements and delivery states

## Current product

The existing seven-page English local workbench is the usable starting point. It runs historical/synthetic replay, explores public compound structures, configures scenarios, selects and advances batches, compares policies, exposes evidence and resumes validated exports. Durable SQLite belongs to the primary API; Streamlit is a session-local fallback. Preserve those workflows during research changes.

## Planned pilot capability

Customer data mapping, a customer-data adapter, pilot report packaging and team onboarding require explicit implementation. A public demo may use current functionality. A proposal must state which release supports the contracted deliverable. User accounts, enterprise hosting, live instruments and automatic wet-lab execution are not current features.

## UX requirements

Show the active task, source origin, protocol identity, predictor/controller status and knowledge cutoff at every result surface. Separate predicted scores, pending commitments, delivered active labels and missing outcomes. Deadline results need accepted/spent/reserved exposure plus late-result counts. A comparison should show learned-action share and explicit fallback, including zero learned actions.

Add research controls only after the scientific contract exists. The UI should not expose implementation jargon unless it helps the scientist make a decision. Provide sensible presets with exact exported settings. Keep accessible keyboard operation, visible focus, reduced-motion support and genuine molecular structures. A synthetic descriptor fixture should not display an invented chemical drawing.

## Product acceptance

The user can understand the campaign, take a valid action, see why it was selected, wait/advance, inspect delivered outcomes and reproduce/export the result. Failure messages explain what was retained and what action is possible. A rejected import leaves the current run intact. A restart does not create outcomes or silently rerun accepted work. No visual redesign can weaken those contracts.

## Full-text review additions

Before new-study acceptance, the registry must retain assay AID/phenotype and discrepancy resolution; the runner must distinguish uniform and known-hit starts; baseline reports must identify selector and update schedule; metric exports must carry numerator/denominator and definition version; and compute reports must separate actual policy time from simulated assay time. A proposed external backend must pass the same public-observation and accounting checks. All these additions remain PLANNED.
