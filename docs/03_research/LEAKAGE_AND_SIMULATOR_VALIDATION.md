# Leakage audit and simulator validation

## Information contract

The selection process receives public descriptors, previously delivered outcomes and allowed operational metadata. Oracle labels and future realized outcomes remain private. Test this boundary at the serialized policy observation and API response, not only inside a Python class. An isolated process prevents accidental imports for built-in code; it is not a security guarantee against a local owner with source access.

Prevent indirect leakage through source row ordering, class-stratified initialization, cache keys, duration/cost generators, target identifiers that encode outcomes, prior benchmark models and final-test tuning. Public pool features may be used only under a declared transductive or inductive contract. Scaling, calibration and feature selection must follow the same contract for every method.

## Checkable simulator cases

Create tiny private truth tables with two or three candidates and known durations/costs. Compute feasible actions and optimal outcomes by enumeration. Verify that the engine matches those results, that simultaneous events have the documented order, and that no method can recover a hidden result early. These tests target meaningful transitions rather than duplicating implementation statements.

The common-delay invariance check is especially important. If final acquisition is unchanged and only time is rescaled, report that property. Deadline and heterogeneous-duration scenarios must produce identifiable tradeoffs on at least one constructed case. A simulator that cannot express the claimed mechanism cannot evaluate it, regardless of model complexity.

## Accounting and reproducibility

Reject duplicate, pending, already-seeded and unaffordable candidates atomically. Reserve once, settle once and retain commitments at deadlines. Verify restart with pending work and no clock advancement. A saved state restores public history and reconstructs private truth from the exact resource; it must not replace a missing dataset with an invented oracle.

## Validation layers

1. Contract tests establish correct information and accounting behavior.
2. Enumerated toy cases establish scheduler semantics and objective consistency.
3. Public historical replay establishes retrospective empirical behavior.
4. Measured laboratory timestamps/costs, if later available, assess operational realism.
5. Prospective experiments, if later performed, assess actual workflow value.

Passing one layer does not imply the next. The first paper may responsibly report the first three with explicit assumptions. The physical process connection needed for a validated Digital Twin remains outside the current evidence.

## Added provenance and negative controls

Block a frozen task record with unresolved phenotype/release conflicts. Test that uniform initialization never inspects labels to choose IDs; test a conditional-known-hit sensitivity separately with its declared label access. Verify that frozen-model arms do not refit and that no-active similarity fallbacks are logged.

Construct paired pending scenarios where feasible IDs are equal but similarities to pending compounds differ. Confirm that duplicate exclusion is shared by both arms, the pending-aware score can alter a choice and the blind arm does not read the treatment summaries. Verify metric toy cases for fixed-FPR versus ranked-fraction enrichment and exclude initial actives from all new-discovery endpoints.
